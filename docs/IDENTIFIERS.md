# Donegal Townlands: Identifier Registry

Status: WP2 implementation
Date: 2026-11-01

## Purpose

The registry records permanent identifiers for established research entities. An
identifier is assigned when a research entity is formally established, not when a
source record is imported. Deterministic observation IDs are generated by the
source-specific processing workflow and are not entered in this registry.

## Identifier format

Research entity identifiers use UUID version 4. They are random UUIDs and carry
no embedded meaning about a person, place, source or date.

A manual place that has no Logainm record uses the `dt-place:<uuid-v4>` form.
A place represented by Logainm uses its Logainm ID as its place key and does not
receive a second project UUID merely for the sake of this registry.

The registry supports these entity types: `person`, `family`, `property`, `place`,
`source-record` and `assertion`.

## Registry

The single registry is `data/research/identifier_registry.csv`, with columns:

| Field | Meaning |
|---|---|
| `id` | Permanent identifier |
| `type` | Entity type |
| `status` | `active`, `merged`, `split` or `retired` |
| `successor` | Replacement identifier or identifiers, separated by semicolons |
| `date` | Date the registry status was recorded, ISO format |
| `reason` | Reason for registration or status change |

Identifiers are never reused. Retired identifiers remain in the registry.
A lifecycle change is recorded by appending another row for the same ID:
the original `active` row remains untouched, followed by a `merged`, `split`
or `retired` row. This is a history event, not a new identifier. A terminal
status must have one or more successors already present in the registry and
its reason must point to the relevant entry in `DECISIONS.md`. The type cannot
change, and a terminal status cannot be changed again.

## Append-only rule

The committed Git version of the registry is the baseline. The validator
requires the current file to begin with the exact bytes of that committed
version. New rows may be appended. Existing rows may not be rewritten,
reordered or removed.

When first installing WP2, commit the header-only registry file before
registering the first entity. This establishes the initial Git baseline.
Subsequent registry additions are checked against that baseline.

This protects the registry against accidental edits in the working tree.
Git history and repository review remain the audit trail for committed changes.

## Commands

From the repository root:

```bash
python tools/identifiers.py self-test
python tools/identifiers.py validate
python tools/identifiers.py new --type person --reason "Established from reviewed evidence"
python tools/identifiers.py new --type place --manual-place --reason "Place absent from Logainm; see research note"
python tools/validate.py
```

The `new` command prints the new identifier and appends one active row.
The reason is required. Use `--manual-place` only for a place that is not
represented by Logainm.

For a merge, split or retirement, first record the decision in `DECISIONS.md`,
then append a lifecycle event. Example:

```bash
python tools/identifiers.py transition --id "EXISTING-UUID" --status merged --successor "SUCCESSOR-UUID" --reason "Merged after review; see DECISIONS.md#merge"
```

For a split, list all successor IDs separated by semicolons. Every successor
must already be registered. The original active row is never edited.

## Validation

`tools/validate.py` checks the registry schema, UUID v4 format, duplicate IDs,
successor references, required decision pointers and append-only Git baseline.
The unit tests include explicit attempts to rewrite and remove a committed line,
and a 10,000-ID generator test.
